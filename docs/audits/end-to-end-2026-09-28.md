# September 28 stability and reporting audit — 1.4.8

## Production evidence before changes

Read-only fleet snapshot at 2026-09-29 05:35 UTC: 27 registrations, 13 connected Windows agents on 1.4.7, seven running Quantus GPU processes and one running Nanominer RandomX CPU process. Six stopped SRBMiner GPUs retained file/preparation failures: KAM_Z1, PGZ9, PG_GH1, PG_Z3, PG_Z6 and PG_Z8. Earlier exact-path checks found missing executables and no matching Defender detections; the cause remains unconfirmed. Their explicit earlier repair attempts failed at archive preparation, but generic diagnostics misleadingly described an executable launch failure. This audit issued no live mining, repair or update commands.

PG_Z4 reports both mining and hardware observations several minutes behind server receipt while its connection is current. Receipt differences now expose possible system-clock or transport delay without fabricating fresh readings. Check that PC's system time during its physical visit. Offline agents and unknown versions cannot be repaired by a backend deployment.

## Repairs

1. **Preparation versus launch:** staged miner distribution attaches its failed operation to errors, including download/write failures. Native diagnostics retain operation/code/path, backend normalization retains the bounded stage and syscall, and admin/client troubleshooting displays them. Historical diagnostics identify their own engine instead of assigning an old XMRig version to a newly selected Nanominer profile.
2. **Repair truthfulness:** a completed file preparation is followed by verification. Unavailable files now return failure through the existing native → renderer → command-result path. No automatic retry or mining start is introduced.
3. **Nanominer shares:** aggregate `Total shares` includes rejects. Accepted equals total minus rejected; impossible or unsafe counters are discarded, rolling summaries excluded, original native timestamps retained. The upstream [issue 309 log sequence](https://github.com/nanopool/nanominer/issues/309) demonstrates one accepted and one denied submission becoming total 2/rejected 1. This fixes live CPU shares previously shown as unavailable.
4. **Current rejection alerts:** require a running, unpaused process and a fresh counter from its current run. Messages identify GPU/CPU and actual engine, not legacy slot IDs. Counts are explicitly lifetime counters for this run, not a time-window rejection percentage.
5. **Clock observability:** status-message timestamps produce `agentClock` (reportedAt, receivedAt, differenceSeconds). Discrepancies over 30 seconds produce a current `clockWarning`; it expires with telemetry. Server receipt includes transport delay, so this is not a measured clock correction. Rate/history/sensor timestamps and freshness thresholds are unchanged.
6. **Download lifecycle:** watch real transferred-byte progress, cancel after five idle minutes or two hours overall, retain transfer ownership until upstream settles, reject late completion after cancellation, and retry on the next normal check. If upstream cancellation itself never settles, the UI explicitly advises restarting the app. Missing verified completion becomes an error instead of permanently holding the available/downloading state. Renderer/diagnostic notification exceptions cannot abort controller cleanup. No change to explicit installation or autoInstallOnAppQuit=false.

7. **Log severity:** live PG_R2 error history contained Nanominer’s ordinary startup reboot-policy sentence. The client now classifies only that exact known sentence as informational, while real file-write, pool and fatal failures remain errors. Historical stored logs are unchanged.

## Verification

Validation passed: **94 client tests and 120 backend tests**, plus admin and client production builds.

Client and backend regressions cover staged write errors, final-inspection repair failure, Nanominer accepted/rejected/zero/invalid/rolling counters, clock warnings without timestamp rewriting, stale/current-run rejection filtering, HTTP/WebSocket diagnostic field parity, download stall/cancellation/late events/missing completion and failed notification isolation. Existing fake-process ownership, independent CPU/GPU Stop, reconnect, expired/revoked/read-only keys, saved resume and command-confirmation regressions remain in the full suites.

The actual installed electron-updater NSIS and AppImage implementations use inert loopback files to verify 1.4.7 → 1.4.8 feed refresh, checksum rejection and persisted resume compatibility. They do not execute an installer. Admin and client production builds are checked. Browser verification uses disposable synthetic rigs, not production: direct controls, progress/failure toasts, chart/totals, clock warning and diagnostic presentation, plus a 390px outer fleet fixture (379px content with scrollbar, scrollWidth=clientWidth) and a backend failure state retaining clearly marked previous data. The client fixture displayed 51 accepted / 3 rejected from Nanominer total 54, at 7.25 kH/s.

No real Windows installer, Windows quarantine behavior or miner executable was exercised in this audit. Existing engine packages remain pinned. Published package integrity and synthetic tests cannot certify each rig's drivers, antivirus policy, network or update relaunch. Supported clients naturally detect/download this release; installation still needs an explicit request. Offline and blocked rigs remain physical follow-up work.

# Fleet regression repair — September 15, 2026

This pass responds to regressions observed after the 1.4.3 release. Earlier passing unit tests and cross-built packages did **not** establish Windows runtime compatibility. The previous audit claims must be read with the findings below. No live mining commands or miner executables were used during verification.

## Findings and repairs

- **Windows Nanominer output was lost.** The older client tailed its log files; the replacement depended on redirected stdout and set `noLog=true`. PG_Z2 reported an owned, running Nanominer 3.10.0 GPU process and fresh power/temperature, but no process logs or hashrate observations were present. Restore file output with upstream `logPath=miner.log`, in each CPU/GPU process's separate working directory. The native manager owns the reader, follows files created after launch, bounds reads to 256 KiB per poll, preserves UTF-8 and the native observation timestamp for newly appended bytes, handles truncation/replacement, and closes the reader on confirmed exit. Nanominer stdout is drained without duplicating the canonical log stream; stderr remains available. A fresh run clears the old file before spawning. The active log grows during that run; it is not an archival log, and is replaced at the next start. Managed application diagnostics remain separately bounded. Upstream reference: [Nanominer logging options](https://github.com/nanopool/nanominer#logpath).
- **Daily controls became cumbersome.** Restore direct Play/Pause on rig rows and details, Play/Pause selected, and Play/Pause all. All means a snapshot of active inventory across every page and filter, excluding offline/unsupported rigs. Play targets enabled reported CPU/GPU processes and avoids GPU scope on CPU-only rigs. Pause targets ALL to cancel pending starts even when process telemetry is absent. Advanced actions, commands, logs, grouping, tags, saved views, sensor columns and charts remain available. Each rig shows dispatch/confirmation/failure separately from observed mining state. Bulk quick controls dispatch groups of eight, retain independent receipts, and stop unsent Play batches when a newer Pause is requested.
- **Status and default ordering obscured the fleet.** Mining is green, connected/stopped blue, offline rose, and stale/error amber. The default UI order is mining, other connected rigs, overdue rigs, then offline, with a stable name/ID tie-break. `sort=activity` is available through the same API pagination. Offline processes no longer claim to be currently stopped. Last contact uses `lastSeen` even if the historical record has no new-protocol telemetry. Unknown legacy versions are explicitly labeled as not sent. Charts are below the list and their history query runs only when expanded.
- **Older update resume intent was discarded.** Releases through 1.1.3 stored only `minerIds` and `savedAt`; newer readers required source/target versions and deleted that old format. Accept only that exact legacy shape within its original ten-minute window, once, with recognized process IDs. Modern resume intent remains bound to the requested version with a two-hour expiry. Already discarded intent cannot be recovered; an operator must explicitly start those stopped rigs.
- **Registration could remain silently incomplete.** Native saved server enablement now restores the connection even when the renderer's old binding flag is missing. Explicit Unbind persists disablement. An open socket without a registration acknowledgment retries every 15 seconds; stale sockets/timers retire on disconnect and acknowledgment. Connection/registration errors are visible in the desktop connection panel.
- **Docker incorrectly reported the live backend unhealthy.** Its health check resolved `localhost` to IPv6 while the app listened on IPv4. Use `127.0.0.1` for the readiness request. Keep database readiness separate from liveness.
- **Disconnect diagnostics lacked the cause sent by the transport.** New agent-disconnected events include the WebSocket close code/reason when available, without inventing causes for historical events.

## Live evidence and remaining limits

Read-only production inspection initially found 27 active inventory records: ten connected, one mining, seventeen disconnected. Eleven disconnected records last reported before this upgrade (some months earlier); four had legacy protocol and no reported version; KAM_Z1 and KAM_Z6 had registered 1.4.3 successfully and disconnected hours later. There was no current update installation reported on those two rigs. The user could not inspect those PCs during this pass, so their later disconnect cause remains **unresolved**. Do not equate older inventory with seventeen confirmed updater failures, or claim this release remotely revives disconnected apps.

PG_Z2's exact runtime fix still requires the new Windows client and a subsequent observed hash sample. No Windows installer execution, hardware benchmark, or Defender behavior has been verified here. Existing 1.4.3 clients require an explicit installer action; publishing an update does not silently install it. Offline machines require the app/network to return before remote control works.

## Verification

Behavioral tests cover file-only native output → parser, observation age, repeated reads, UTF-8 boundaries, truncation, confirmed-stop ownership, legacy update migration and rejection cases, registration acknowledgment retry, quick-control scope eligibility, stale/offline/zero labels, and cursor ordering. Full client/server suites and production web builds are run before release. Browser checks use disposable rigs and simulated Electron; final deployment/release results are recorded separately when completed.

Validation completed before publication: **71 client tests and 94 server tests passed**. Admin and client production builds passed. At 390px and desktop widths, the fixture kept direct controls and distinct states; group/tag/attention filters remained accessible. Simulated row Pause, fleet Pause, fleet Play and failure handling were checked. A second fixture connected the real client renderer to the real disposable admin with the legacy browser binding flag absent: native enabled config restored registration; admin Play produced confirmed CPU/GPU results, 7.25 kH/s CPU and 61.50 MH/s GPU samples and process logs; admin Pause stopped both simulated processes. No real miner or production control command was executed.

Windows file-time check: [Microsoft documents](https://learn.microsoft.com/en-us/windows/win32/sysinfo/file-times) that last-write time is not fully updated until writable handles close. Owned fresh logs therefore timestamp newly observed bytes instead of depending on `mtime`. Unchanged files produce no new observations; long monitoring gaps discard backlog and wait for new output. Oversized backlogs skip old bytes with a diagnostic and reset incomplete lines. A regression test holds write time fixed while appending output.

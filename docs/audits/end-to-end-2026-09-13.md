# End-to-end reliability follow-up — desktop 1.3.2

This audit traced configuration delivery, command execution/replay, update completion, telemetry normalization, sensor aging, recovery decisions and their admin/API presentation. It follows the [desktop third pass](client-2026-09-13/third-pass.md) and [backend second pass](backend-admin-2026-09-12/second-pass.md).

## Implemented repairs

1. **Zero-rate recovery continuity.** A reconnect previously retained `zeroSince` from the previous connection, allowing recovery immediately after an unobserved gap. Recovery continuity now requires a recent prior status and the same process launch (start time, PID, algorithm and running state). Reconnects and reporting gaps reset the timer. Out-of-order rate preservation happens before zero-timer calculation and cannot copy a previous launch's rate or overwrite a paused process.
2. **Independent sensor freshness.** The renderer already sent native CPU/GPU observation times, but server normalization discarded them in favor of the status envelope time. CPU usage, CPU temperature, memory and individual GPU timestamps now survive ingestion and API reads. Readings expire independently after 60 seconds, including on reads without new telemetry. Invalid timestamps and timestamps more than five seconds ahead are unavailable. Older agents without provider timestamps retain the envelope fallback. Empty envelopes do not count as rigs supplying sensor measurements.
3. **Optional telemetry robustness.** Impossible numeric dates no longer throw during ISO formatting. Process overrides, miner versions, pool metadata and share counters are bounded/typed; malformed optional values become unavailable without dropping the entire status. Admin rendering also tolerates old malformed override lists.
4. **Update handoff replay.** A transport reconnect or duplicate command previously converted a completed installer handoff into an unknown-outcome failure. The client now replays the persisted handoff receipt as running without invoking the installer again. The server still exclusively confirms success through target-version registration and preserves terminal timeout/cancellation. The final database update also rechecks its deadline.
5. **Expired resume cleanup.** An expired update-resume record previously survived indefinitely when the old app launched. Validation now runs before the old-version preservation rule, clearing expired or malformed intent.
6. **Admin usability.** Command choices, buttons and history use readable labels while keeping stable API action names. Rig details show original sensor observation times separately from the report time.

## Validation

Final verification passed: **70 backend tests**, **48 desktop tests**, the admin production build and the desktop renderer production build. The suites overlap on shared native/protocol coverage. Tests use disposable MongoDB and fake processes only. New coverage includes a real synthetic WebSocket reconnect followed by a REST read, independent sensor expiration, malformed optional telemetry, empty sensor coverage, persisted handoff replay/duplicate suppression and expired old-version resume cleanup.

Loopback UI checks verified desktop 1.3.2 startup, a stale 95°C sample shown as unavailable alongside fresh CPU usage, readable action labels, and retained fleet data with an explicit network-error/staleness notice after fixture shutdown. The update dialog fit within a 640-pixel viewport by DOM measurement; the screenshot surface still clips its right edge, limiting complete visual verification.

## Limits and rollout

No live fleet command, mining binary, updater installation or deployment was run. This pass does not establish Windows Defender behavior, CPU/GPU performance, native sensor calibration or real NSIS/AppImage upgrade reliability. Those release checks remain in [the release guide](../../client/RELEASING.md). No miner versions, fees, authentication boundaries or distribution hashes changed. Deploy backend/admin together for the sensor contract; update clients to 1.3.2 for receipt replay and resume cleanup. Existing clients continue reporting without API keys.

The server's connection/dispatch coordination remains process-local: this pass does not add multi-instance active/active operation. Persistence outages still report unavailable/unknown outcomes; operators must inspect rigs before retrying commands whose execution was not confirmed. Older stored metrics are not rewritten or retroactively given provider timestamps.

# End-to-end reliability follow-up — desktop 1.3.2

This audit traced configuration delivery, command execution/replay, update completion, telemetry normalization, sensor aging, recovery decisions and their admin/API presentation. It follows the [desktop third pass](client-2026-09-13/third-pass.md) and [backend second pass](backend-admin-2026-09-12/second-pass.md).

## Implemented repairs

1. **Zero-rate recovery continuity.** A reconnect previously retained `zeroSince` from the previous connection, allowing recovery immediately after an unobserved gap. Recovery continuity now requires a recent prior status and the same process launch (start time, PID, algorithm and running state). Reconnects and reporting gaps reset the timer. Out-of-order rate preservation happens before zero-timer calculation and cannot copy a previous launch's rate or overwrite a paused process.
2. **Independent sensor freshness.** The renderer already sent native CPU/GPU observation times, but server normalization discarded them in favor of the status envelope time. CPU usage, CPU temperature, memory and individual GPU timestamps now survive ingestion and API reads. Readings expire independently after 60 seconds, including on reads without new telemetry. Invalid timestamps and timestamps more than five seconds ahead are unavailable. Older agents without provider timestamps retain the envelope fallback. Empty envelopes do not count as rigs supplying sensor measurements.
3. **Optional telemetry robustness.** Impossible numeric dates no longer throw during ISO formatting. Process overrides, miner versions, pool metadata and share counters are bounded/typed; malformed optional values become unavailable without dropping the entire status. Admin rendering also tolerates old malformed override lists.
4. **Update handoff replay.** A transport reconnect or duplicate command previously converted a completed installer handoff into an unknown-outcome failure. The client now replays the persisted handoff receipt as running without invoking the installer again. The server still exclusively confirms success through target-version registration and preserves terminal timeout/cancellation. The final database update also rechecks its deadline.
5. **Expired resume cleanup.** An expired update-resume record previously survived indefinitely when the old app launched. Validation now runs before the old-version preservation rule, clearing expired or malformed intent.
6. **Admin usability.** Command choices, buttons and history use readable labels while keeping stable API action names. Rig details show original sensor observation times separately from the report time.

## Validation

Final verification passed: **70 backend tests**, **48 desktop tests**, the admin production build and the desktop renderer production build. The suites overlap on shared native/protocol coverage. Tests use disposable MongoDB and fake processes only. New coverage includes a real synthetic WebSocket reconnect followed by a REST read, independent sensor expiration, malformed optional telemetry, empty sensor coverage, persisted handoff replay/duplicate suppression and expired old-version resume cleanup.

Loopback UI checks verified desktop 1.3.2 startup, a stale 95°C sample shown as unavailable alongside fresh CPU usage, readable action labels, and retained fleet data with an explicit network-error/staleness notice after fixture shutdown. The update dialog fit within a 640-pixel viewport by DOM measurement; the screenshot surface still clips its right edge, limiting complete visual verification.

## Limits and rollout

No live fleet command, mining binary, updater installation or deployment was run. This pass does not establish Windows Defender behavior, CPU/GPU performance, native sensor calibration or real NSIS/AppImage upgrade reliability. Those release checks remain in [the release guide](../../client/RELEASING.md). No miner versions, fees, authentication boundaries or distribution hashes changed. Deploy backend/admin together for the sensor contract; update clients to 1.3.2 for receipt replay and resume cleanup. Existing clients continue reporting without API keys.

The server's connection/dispatch coordination remains process-local: this pass does not add multi-instance active/active operation. Persistence outages still report unavailable/unknown outcomes; operators must inspect rigs before retrying commands whose execution was not confirmed. Older stored metrics are not rewritten or retroactively given provider timestamps.

## Second end-to-end pass — desktop 1.3.3

This pass revisited Stop supersession, desired-state ordering, restart-only rollouts and the native-output-to-telemetry path.

- **Stop completion race:** after finding an active restart to supersede, the restart could finish before cancellation. The cancellation conflict previously aborted creation of the newer Stop, leaving it queued and undispatched. An already-terminal superseded command is now harmless; storage/transport failures still propagate. A synthetic WebSocket/API regression forces completion at that exact point and verifies the newer whole-rig Stop is dispatched.
- **Whole-rig/scoped intent ordering:** timestamps alone could tie within one millisecond, causing an older ALL intent to mask a newer CPU/GPU intent in recovery decisions. Whole-rig commands now atomically write ALL, CPU and GPU desired-state entries. Recovery uses the scoped entry on equal timestamps, so a later scoped command is unambiguous. These entries describe desired intent, not proof of execution.
- **Idle rollout behavior:** `restartRunningOnly` previously still issued Stop for an idle process, potentially canceling native pending recovery. It now reports the process skipped without Stop/Start. Configuration delivery still updates desired settings before this decision; it takes effect at the next launch. The decision uses the client's current observed process state, so inspect drift when the native state changes concurrently.
- **Interleaved output:** stdout and stderr used one line buffer. A stderr warning between two chunks of a stdout hashrate line could corrupt parsing and produce missing rates/log lines. Native output now identifies its stream; renderer buffers are independent per stream and reset when `runId` changes. Older events without stream identity default to stdout. The raw console can still show arrival order; parsed rate and centralized log lines use the separated buffers.

Validation passed: **74 backend tests**, **50 client tests**, and both production builds. Shared native/protocol tests overlap between suites. The loopback desktop fixture emitted a split stdout hashrate with a stderr warning in between; the UI displayed the expected **7.25 kH/s** and returned to Stopped after simulated Stop. No mining executable ran. Windows/Linux hardware, real installers and production deployments were not exercised; the earlier release limits remain. No authentication boundary, upstream binary release, fee or miner configuration format changed.

## Third end-to-end pass — desktop 1.3.4

This round focused on log backpressure, local disk-write backlog, API attention filtering and dashboard agreement.

- **Network log overflow:** creating an overflow warning previously evicted another buffered line. Retrying while the socket was blocked repeatedly changed the queue and count. Overflow warnings are now constructed outside the queue; failed sends leave the queue/count untouched, and successful sends consume only their batch's real entries. Regression tests repeat failed sends before recovery and verify exact counts.
- **Native logging backlog:** disk rotation bounded stored files but the promise chain of pending writes was unbounded. Pending writes are now capped at 256; omitted entries are counted in a single diagnostic after the backlog drains. Enqueued details are serialized once and detached from later mutations. Unserializable/undefined JSON values cannot throw outside the logger. Tests cover a synthetic write storm, recovery, mutation and disk failures.
- **API/dashboard filter agreement:** `attention=false` was accepted but treated as no filter. It now selects only unflagged rigs consistently across rig lists, fleet summaries and scoped incidents. The admin provides All rigs / Needs attention / No attention flagged choices. No attention flag is not equivalent to verified hardware health, especially in maintenance.

Validation passed: **76 backend tests**, **51 client tests**, and both production builds. Tests use disposable data and fake processes. The loopback dashboard showed five flagged rigs with `attention=true`, and seven unflagged rigs with zero attention incidents using `attention=false`; the summary matched each selection. The attention control was checked at a 640-pixel viewport, although screenshot clipping limits complete visual verification. After the fixture became unavailable, Refresh showed a network error and an explicit stale-data notice while retaining the last received fleet data. No mining executable, real hardware, installer or deployment was exercised. No authentication boundary, command action, upstream miner release or protection policy changed. Remote logs still have no durable database acknowledgment; the fixes bound resource use and correct loss reporting rather than guaranteeing delivery. The earlier real-hardware and installer limitations remain.
